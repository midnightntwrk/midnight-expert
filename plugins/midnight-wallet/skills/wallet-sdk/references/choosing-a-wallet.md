# Choosing an Onboarding Route

Four ways to get a user onto Midnight, and the four questions that actually separate them:
**does the user install anything, who holds the keys, who generates the proof, and who pays the fee.**

Answer those and the choice is usually forced. Everything below is as of **2026-10-22**; verify the
version-specific claims before you quote them to a user.

| Route | Install | Keys | Prover | Fees | Works today |
|---|---|---|---|---|---|
| **Dynamic** (hosted / WaaS) | none — email or social login | TSS-MPC shares; Midnight signing keys derived through the key-export path | provider's wallet client (remote) | user's own DUST; **no sponsorship on Midnight** | mainnet and preview through `@dynamic-labs/midnight` |
| **1AM** | Chrome/Firefox extension, plus iOS and Android apps | self-custody, keys in device secure storage | in-browser WASM (Halo2 / BLS12-381), plus a hosted Proof Station | user's own DUST; sponsorship not documented | live |
| **Kuira** | none on Android — SDK embedded in your app | self-custody, on-device, passkey-derived identity ("Sigil") | on-device | user's own DUST | Android alpha (`v0.1.0-alpha02`); iOS and React Native stated for later |
| **Lace** | Chrome/Edge extension | self-custody | **local proof server required** (`http://localhost:6300`) | user's own DUST | live; the reference wallet most examples assume |

Backend jobs, CI and AI agents are a fifth case: the wallet CLI (`midnight serve`) and its MCP server,
not any consumer wallet. That is `midnight-wallet:managing-test-wallets`, not this page.

## Decide in this order

1. **Must the user avoid an install?**
   - Yes → **Dynamic** (accept hosted proving and a key-export requirement) or **Kuira** (Android only, self-custody, alpha).
   - No → continue.
2. **Does the privacy model have to hold against the provider itself?**
   - Yes → **1AM** (shielded by default, proves in the tab) or **Kuira** (proves on device).
   - No, a hosted wallet is acceptable → **Dynamic**.
3. **Do you also need Cardano assets, staking, or the wallet developers will test against?**
   - Yes → **Lace**, and budget for the local prover.
4. **Is your surface a browser DApp?**
   - Then you are integrating through the DApp Connector (`window.midnight`), and the wallet list above is your user base — support 1AM and Lace first, feature-detect everything else.

## The constraints that decide more often than the wallet does

- **Funding is the real gate, not the wallet.** Every route creates an *empty* wallet. Midnight DUST is
  generated by registered unshielded NIGHT and accrues over time — roughly 12 hours on mainnet. Budget an
  explicit state machine: `created → funded (unshielded) → registered → dust accruing → spendable`.
  A product that hides those stages shows a new user an empty screen and a disabled button.
- **No fee sponsorship on Midnight through Dynamic.** Their gasless feature is scoped to EVM and Solana.
  On 1AM, sponsorship is not documented either. Assume the user funds their own fees unless you
  pre-fund and pre-register on their behalf.
- **Cross-pool transfers are not an app feature.** Shielded and unshielded NIGHT are different token types
  in different pools. Dynamic's connector does not convert between them, so a shielded-first experience
  needs a *shielded* funder (an exchange withdrawal or a self-custody wallet sending to `mn_shield…`).
- **Proving location is the privacy boundary.** In-tab (1AM) and on-device (Kuira) proving keeps the
  witness on the user's machine. Hosted proving (Dynamic) means the witness is handled in the provider's
  client. Lace keeps it local but needs a local server — a non-starter for consumer onboarding.
- **Network identity is a footgun, not a detail.** Network ids are `mainnet`, `preview`, `preprod`,
  `undeployed`; only `mainnet` is connector-standard. Anything that infers the network from a name
  substring will read `Preview`/`Preprod` as mainnet. Resolve it explicitly and assert it in staging.

## Do not choose

- **Lace for consumer onboarding** — a local proof server is an install-then-configure step most users will not finish.
- **Kuira if iOS is in scope this year** — Android only today.
- **Dynamic if you cannot enable Private Key Exports**, or if the shielded witness must stay on the user's device. Ask the provider directly; do not infer it from the word "non-custodial".
- **1AM if you need documented fee sponsorship** — it is not published.

## How to settle it in an hour

Before you commit to a route, run the same six checks against it:

1. Feature-detect the connector (`typeof api.getProvingProvider === "function"`) rather than assuming methods exist.
2. Log the resolved network id in every environment; assert staging reports staging.
3. Receive unshielded NIGHT and read the balance three ways (formatted, raw, per-token).
4. Register DUST and record the real time-to-first-spendable-DUST on your target network.
5. Send to a shielded address and confirm the pool routing — and that cross-pool is refused, as documented.
6. Kill the tab mid-build and confirm the reserved inputs come back (`revertTransaction` / `revertAllPending`).

If step 4 exceeds the patience of your onboarding flow, the route is wrong for this product regardless of
how good the wallet is.
